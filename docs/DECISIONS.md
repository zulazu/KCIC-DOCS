# KCIC Connect — Engineering Decisions

| ID | Decision | Rationale / authority |
|---|---|---|
| DEC-001 | Trusted left sidebar uses maroon `#8B1A1A` background with white text, gold active indicator. | Latest explicit Product Owner instruction (“use #8B1A1A as side bar color”) overrides DESIGN_SYSTEM §5.2 white sidebar default. White text on maroon is 9.29:1 (AA). Active state uses tint + 3px gold edge + `aria-current`, not color alone. |
| DEC-002 | Backend streaming is used for preview/download; signed URLs are not issued. | Allows authorization on every request and immediate revocation; avoids signed-URL leakage/TTL bookkeeping. ARCHITECTURE §9.5 permits either. |
| DEC-003 | Session persistence via Spring Session JDBC (PostgreSQL). | Stable sessions across restarts, account-wide invalidation, no Redis (deferred). ARCHITECTURE §7.2 baseline. |
| DEC-004 | Maven 3.9.9 provisioned under `tools/` (gitignored); Spring Boot 3.5.16; compile `--release 21`. | No system Maven/Gradle installed; JDK 23 present. Release 21 keeps the artifact portable while running on JDK 23. |
| DEC-005 | File policy seeded as `PILOT_DEFAULT` (PDF, DOC/DOCX, XLS/XLSX, PPT/PPTX, TXT, CSV; 25 MB) marked PROVISIONAL. | Pilot must be operable without inventing final company policy. Business owner must approve/replace before go-live (PRD open question). |
| DEC-006 | Login lock: 5 failed attempts → 15-minute lock; generic invalid-credential message. Password policy: minimum 12 chars, cannot equal username/email. | ARCHITECTURE §12.1 requires attempt/lock policy; values are configurable. Password reset uses admin-set temporary password + forced change. |
| DEC-007 | Classification is metadata plus audit; access is not silently inferred from classification. RESTRICTED documents get no broader discovery. Document access = role capability + scope + ACL (or creator/owner relation). | SCHEMA §7.3 says final classification rules need policy approval; avoids inventing business rules. |
| DEC-008 | Unit-scoped role assignments grant capability over resources owned by that unit (documents’ owner unit, workspace owner unit). Cross-unit access still requires ACL. | Implements meaningful organization scope without global leakage; covered by negative tests. |
| DEC-009 | `CLOSED` request state is reachable by requester/approver closing a FULFILLED request (administrative close). | PRD REQ-06 permits simple pilot closure rule. |
| DEC-010 | Notifications are per-recipient rows created inside the same transaction as the triggering business action. | SCHEMA §12; no external delivery in pilot. |
| DEC-011 | Request attachments are deferred for the pilot (superseded by DEC-034); request evidence travels through description, fulfillment notes, and linked/uploaded documents. | SCHEMA §9.2 permits optional attachments but PRD does not require them for acceptance; deferring avoids a second upload path before templates/distribution are built. |
| DEC-012 | Distribution grants are `USER` ACL entries with provenance rows; revoke/expiry disables only those grants. | SCHEMA §10.4; ARCHITECTURE §8.3. |
| DEC-013 | Bootstrap administrator is created only when the user table is empty and always requires a password change at first login. | Prevents a known seed credential from remaining valid; aligns with DEC-006. |
| DEC-014 | JPQL search queries take a non-null `keyword` and use `:keyword = ''`, never `:keyword is null`. | PostgreSQL cannot infer the type of a nullable String parameter and binds it as `bytea`, producing `lower(bytea) does not exist`. Split status/all queries avoid nullable enum typing. |
| DEC-015 | Frontend hides navigation from a capability snapshot returned by `/auth/me`; every API independently re-authorizes. | UX-level hiding only (AGENTS §6.2); backend remains the authority (AGENTS §8.1). |
| DEC-016 | Administration UI is page-based (list → detail) with dialogs only for short confirmations/forms; native `<dialog>` supplies focus trapping and Escape handling. | AGENTS §6.2 and DESIGN_SYSTEM interaction rules; avoids hand-rolled modal stacks. |
| DEC-017 | Denial at the resource layer returns `403 RESOURCE_FORBIDDEN`; missing global capability returns `403 ACTION_FORBIDDEN`. Both carry `requestId` and never reveal whether the resource exists. | Lets the UI distinguish "you lack this feature" from "this specific item is not yours" without leaking existence; ARCHITECTURE §11.3 error contract. |
| DEC-018 | Workspace creation requires global `workspace.manage`, or unit-scoped `workspace.manage` on the selected owner unit. Workspace and folder reads require `workspace.view` with the same scoping. | Implements DEC-008 scope semantics for the first repository resources; enforced in the application service, not the controller. |
| DEC-019 | Folder invariants are enforced in the service inside one transaction: parent ACTIVE in the same workspace, case-insensitive unique sibling name among non-archived folders, no self/descendant parent, archive blocked while non-archived children exist, ARCHIVED workspace is folder read-only. | SCHEMA §6.2 invariants; backend is authoritative (AGENTS §8.1). |
| DEC-020 | Workspace status uses a fixed transition table (ACTIVE↔INACTIVE, both → ARCHIVED, ARCHIVED → ACTIVE); setting the current status is a no-op, an invalid target returns `409 CONFLICT`. | Prevents contradictory lifecycle writes and makes repeated submits idempotent. |
| DEC-021 | Stale workspace/folder edits are rejected with `409 CONFLICT` via version checks rather than merged last-write-wins. | ARCHITECTURE §7.5 optimistic locking; surfaces concurrent edits to the user. |
| DEC-022 | Dialog forms handle error/state resets with per-open helpers (`actionError` and form errors cleared, content conditionally rendered so the form remounts) because the shared native `<dialog>` keeps children mounted between opens. | Observed defects: stale error banners and a select whose value fell back when its option was conditionally removed. Documented so future dialogs follow the same pattern. |
| DEC-023 | File-policy allowlist inputs split only on commas/newlines; tokens containing spaces are rejected by backend validation rather than silently re-split. Frontend maps array-index field errors (`allowedExtensions[1]`) back to the field. | A space in a saved allowlist would have widened/narrowed policy silently; explicit rejection keeps the policy exactly what the admin typed. |
| DEC-024 | Storage is accessed through a `StorageAdapter` port with an S3-compatible (MinIO) adapter and a filesystem adapter for dev/tests. Buckets stay private; files are streamed through the API after authorization, not via signed or public URLs. | ARCHITECTURE §9.5 and AGENTS §10; keeps authorization on every read and immediate revoke. Filesystem provider lets the pilot run locally without weakening key/checksum semantics. |
| DEC-025 | The SYSTEM_ADMIN role does not implicitly grant document content capabilities. Content access requires document capabilities plus scope/ACL or creator/owner relation. | AGENTS §8.2 default-deny and §8.5 ACL-by-resource; separates platform administration from business document access. Covered by `employeeAndSystemAdminCannotReadUnownedDocumentContent`. |
| DEC-026 | Upload validation runs backend-only in order: extension and declared MIME against active file policy, size ceiling, magic-byte sniffing, then storage write; object keys are random UUID-derived, original names stay metadata, and SHA-256 is persisted. | AGENTS §8.13–8.15 and §10; prevents renamed executables and path traversal via filenames. Magic bytes are validation, not antivirus (residual risk documented). |
| DEC-027 | A new upload or an explicit promote closes the CURRENT version to SUPERSEDED and makes the target CURRENT inside one transaction; version binaries are immutable and external links are versioned `EXTERNAL_LINK` rows restricted to HTTPS. | SCHEMA §7 version invariants and REPO-07; gives one current version without rewriting history. Office links are recorded only (no provider permission sync). |
| DEC-028 | ARCHIVED documents reject new version uploads and external links in the application service even when the actor holds upload/version capabilities; metadata edits remain allowed, and restore returns the document to ACTIVE. | Archive means read-only content in the pilot; capability checks alone would otherwise permit mutations. Frontend hides the same actions to match the backend contract. |
| DEC-029 | Catalog visibility is filtered in the application after loading candidates and the resulting list is paginated in memory; sorting remains server-side over the candidate set. | Current access depends on creator/owner/unit ACL relations that are not yet expressible in one portable JPQL query; correctness over premature SQL complexity. Revisit with ACL pushdown in Phase 5/9 at pilot data volumes. |
| DEC-030 | Owner changes require `ownerChangeReason` (≥5 chars) and `document.update_metadata`; the open `document_owner_history` row is closed and flushed before the new row is inserted, preserving the partial unique index, and `DOCUMENT_OWNER_CHANGED` audit records previous/new owner and reason. | SCHEMA owner-history invariant and audit requirements; explicit flush avoids relying on Hibernate insert ordering. |
| DEC-031 | Display-name lookups for optional owner ids are null-safe (`nameFor`); immutable maps must never receive a null lookup key. | Unit-only ownership has no owner user; `Map.of().get(null)` threw NPE and produced a 500 on metadata updates. Regression covered in `ownerChangeRequiresReasonAndKeepsHistory`. |
| DEC-032 | Resource ACL is evaluated at every visibility surface: document catalog/detail/preview/download/versions, workspace list/get, and folder list. An explicit DENY in any applicable scope (document, folder ancestry, workspace) hides the resource even for global/role assignments; an explicit ALLOW exposes an out-of-unit resource; otherwise role + unit scope decides. Folder grants inherit along the real parent chain via `FolderGrantResolver`. Revoking one grant leaves independent grants intact. | ARCHITECTURE §8.2 deny precedence and §8.3 resource ACL; prior behavior let role scope alone decide workspace/folder reads, so granted out-of-unit users still received 403. Covered by `workspaceAclGrantExposesAndDenyHidesWorkspaceOutsideUnitScope`, `folderViewGrantAppliesToSubtreeOnlyAndFolderDenyHidesTheFolder`, and existing document ACL tests. |
| DEC-033 | Folder create/update/archive remain role/scope capability checks (`folder.create/update/archive`); the ACL allowlist exposes only `workspace.view`, `folder.view`, and document permissions per target type, and `document.manage_access` is never grantable. Duplicate active grants return 409; inapplicable permission codes return 400 with `fieldErrors`. | Keeps Phase 5 ACL scope aligned with the UI and prevents users from minting access-control rights for themselves; manage capability stays with `workspace.manage`, `folder.update`, or `document.manage_access`. |
| DEC-034 | Request attachments are deferred for the pilot; `document_requests` carries no attachment table and the UI exposes no attachment upload. Evidence is the description, fulfillment notes, and fulfillment items (linked or uploaded documents). | Matches PRD acceptance (REQ-01..06) without a second storage path; supersedes DEC-011. Revisit only if UAT requires formal request attachments. |
| DEC-035 | Request routing resolves the approver in order: target document owner user → manager of the owning/target organization unit → `DOCUMENT_ADMIN` (global) → `DOCUMENT_ADMIN` scoped to that unit → `SYSTEM_ADMIN`. If none is active, creation fails with `409 CONFLICT` instead of leaving an orphan request. | PRD REQ-03 requires a deterministic owner/approver; failing fast surfaces missing administration instead of silently routing to the requester. |
| DEC-036 | Request transitions are a server-side table: `DRAFT→SUBMITTED/CANCELLED`, `SUBMITTED→UNDER_REVIEW/APPROVED/REJECTED/CANCELLED`, `UNDER_REVIEW→APPROVED/REJECTED/CANCELLED`, `APPROVED→IN_PROGRESS/FULFILLED/CANCELLED`, `IN_PROGRESS→FULFILLED/CANCELLED`, `FULFILLED/REJECTED→CLOSED`, terminal `CLOSED/CANCELLED`. Invalid or repeated transitions return 409. Only the routed approver may review/decide; rejection requires a reason; cancel is limited to requester/assignee (or request-wide viewers) while open; close is limited to requester/assignee after `FULFILLED`/`REJECTED`. | PRD REQ-04..06 and AGENTS §7.4; the frontend mirrors the table for affordance only, the backend remains authoritative. |
| DEC-037 | Fulfillment is allowed only in `APPROVED`/`IN_PROGRESS`. `ACCESS_GRANTED` creates USER ACL allows for `document.view/preview/download` with `GrantSource.REQUEST` and skips permissions already allowed; `DOCUMENT_LINKED` authorizes each document and snapshots its current version (max 20 per fulfillment); `EXTERNAL_LINK_REGISTERED` accepts HTTPS URLs only and is recorded without implying provider permission changes. The first fulfillment moves `APPROVED→IN_PROGRESS→FULFILLED` in one transaction and completes the pending approval. | SCHEMA §10/§9 fulfills REQ-05 with auditable provenance; reusing the existing ACL evaluator means revoke/expiry semantics stay identical to manual grants. |
| DEC-038 | File fulfillment uses `POST /api/v1/requests/{id}/fulfill/upload` (multipart `documentId`, `file`, `note`, `versionLabel`) through the document-version pipeline (file policy, magic-byte sniffing, private storage). The JSON fulfillment endpoint rejects `DOCUMENT_UPLOADED` with 400. | Prevents bypassing upload validation through the workflow API; keeps one implementation of storage and policy checks (DEC-026). |
| DEC-039 | In-app notifications are per-recipient rows written in the same transaction as the business event: submission notifies the approver; approval, rejection, fulfillment, and cancellation notify the requester (and the counterpart on cancellation). Read state is per user; list/unread-count/mark-read/mark-all are recipient-scoped. The bell polls the unread count every 60 s. | SCHEMA §12 and NOTIF-02; no external delivery in the pilot, and transaction coupling guarantees no notification without the underlying state change. |
| DEC-040 | A distribution has no draft phase in the pilot: `POST /distributions` persists it as `SENT`, creates grants, events, notifications, and audit in one transaction. `GET`/revoke are the only later transitions. | PRD DIST requirements describe send → track → revoke; a draft/scheduling workflow would add states and UI not required for acceptance. Lazy expiry is used instead of a scheduler because no distributed worker platform is allowed (AGENTS §3). |
| DEC-041 | Distribution recipients are snapshotted at send time: users must be ACTIVE, unit recipients expand to the unit's ACTIVE members present then, and the sender is excluded. Later unit membership changes or deactivations do not retroactively add or remove recipients (revoke/account deactivation handles removal). | Makes the delivery set auditable and deterministic; matches SCHEMA recipient rows being the record of who was granted access. |
| DEC-042 | READ means the recipient opened the distribution detail, not that the underlying document was opened. It is recorded once on the first detail read with a `READ` event and `readAt`; senders see `readCount`. | Gives senders a reliable acknowledgement signal without instrumenting every document surface; document opens remain audited separately. |
| DEC-043 | A sender may delegate only an access level it currently holds on that document (`VIEW` ⊆ view; `PREVIEW` requires view+preview; `DOWNLOAD` requires view+preview+download) and only with `document.share`. Revoke is allowed for the sender or a global `distribution.revoke` holder while the distribution is active. | Prevents privilege amplification through distribution and keeps revocation possible for administrators when the sender is unavailable. Evaluated per document at send time; enforced in `DistributionService.requireDelegable`. |
| DEC-044 | Distribution grants are individual `USER` ACL rows linked to the distribution through `distribution_access_grants`. Revoking a distribution or one recipient revokes only linked rows; independent grants from REQUEST, MANUAL, or another distribution stay active. | AGENTS §8.8 and DEC-012; verified in the browser (Employee1 retained MANUAL/REQUEST access after a distribution revoke) and by integration tests. |
| DEC-045 | `/api/v1/access-directory` is readable by principals holding any of `document.manage_access`, `workspace.manage`, `folder.update`, or `distribution.create`; it exposes only active user id/display name/username (max 20 per search), active units, and active roles. | Recipient selection needs a directory, but exposing a full admin directory to every employee would violate least privilege; the capability list matches screens that legitimately grant access. |
| DEC-046 | A template references exactly one existing repository document (`document_id` UNIQUE) and never copies its binary; the published pointer is a composite FK (`current_published_version_id, document_id`) to `document_versions`, so a published version must belong to the same document. Template codes are unique case-insensitively and stored normalized to uppercase. | TEMPLATE-02.3 and SCHEMA §11: one template cannot fork content or point at another document's version; the DB enforces the invariant instead of relying on service code. |
| DEC-047 | Publish requires `template.publish` and defaults to the document's CURRENT version; an explicit `versionId` must belong to that document, be CURRENT, and not WITHDRAWN. `DRAFT→PUBLISHED` and re-publish to a newer CURRENT are allowed; publishing the same version again is a no-op; ARCHIVED template or ARCHIVED document returns 409. Publisher, timestamp, and version are recorded and audited as `TEMPLATE_PUBLISHED`. | TEMPLATE-03.1/3.2 and REPO-07 version semantics; keeps one "published version" pointer without duplicated binaries or silent downgrades. |
| DEC-048 | Governance split: regular users (any `template.view`) see only PUBLISHED templates whose source document they may view; `template.publish|archive` holders see all statuses; `template.create` holders additionally see DRAFT/ARCHIVED templates for documents they can view. Non-visible detail returns 404. Archive requires `template.archive`, retains the version pointer and history, hides the template from the common catalog, and a second archive returns 409. | TEMPLATE-01.1/1.4 and TEMPLATE-03.3/3.4: drafts and archives stay out of the official catalog while remaining auditable for governors; template metadata never bypasses document ACL (AGENTS §8.5). |
| DEC-049 | Template usage (`VIEW`/`COPY`/`DOWNLOAD`) is authorized against the source document, not the template: VIEW/COPY require `document.view`, DOWNLOAD requires `document.download`. Each event is stored against the current published version and audited as `TEMPLATE_USED`; counts are analytics only and never grant access. | TEMPLATE-04.1/4.2: opening a catalog entry must not become a side channel around document permissions; version-scoped events allow adoption analysis per publication. |
| DEC-050 | Catalog reads apply keyword/category/owner/unit/status filters with a Specification, load at most 1000 rows ordered by template name, then filter visibility and paginate in memory (same tradeoff as DEC-029). The response still carries server-computed `totalItems`/`totalPages`. | Access-dependent visibility cannot be expressed in one portable JPQL query; correctness over premature SQL complexity at pilot volumes, with a listed Phase 9 revisit (ACL pushdown). |
| DEC-051 | Non-current template history entries offer a warning-gated download (`document.download`) of that historical document version; inline preview stays on the document detail page. Historical downloads do not create template usage events, which remain scoped to the published version per DEC-049. | TEMPLATE-04.3 requires a warning when a user opens a non-current template; reusing the authorized version-content endpoint avoids duplicating storage logic while keeping adoption metrics comparable across publications. |
| DEC-052 | Template actions (create/update/publish/archive/usage) are audited with `TEMPLATE_*` action codes and safe metadata (`templateId`, `documentId`, `versionNumber`, status transitions) only; template metadata never includes storage keys, signed URLs, or file contents. | AGENTS §8.18 and TEMPLATE-03.2; the audit register must explain governance without becoming a leak surface. |
| DEC-053 | Audit trail read is a global, read-only view gated only by `audit.view` (AUDITOR and SYSTEM_ADMIN); it is not filtered by the viewer's document/unit scope. Search supports actor keyword, action, resource type/id, outcome, and UTC day range with server pagination (≤100 per page), newest first. | AUDIT-01 requires an investigable trail; restricting it to the viewer's own scope would hide exactly the cross-unit activity auditors must see. Mutation endpoints do not exist, and metadata is already sanitized (DEC-052), so the read exposure is limited to safe business facts. |
| DEC-054 | Every route page is loaded with `React.lazy` + a shared `Suspense` fallback (`LoadingBlock`); the AppShell wraps its outlet in the same boundary. | Removes the >500 kB single-bundle warning without changing behavior; deep links and refresh are verified against the dev server, and the built entry chunk is 365 kB (113 kB gzip) with per-page chunks. |
| DEC-055 | Organization units become a typed hierarchy: `COMPANY → DIRECTORATE → DEPARTMENT → DIVISION`; parent-child shape is validated per type, a single active `COMPANY` root is expected, and existing untyped units remain `unit_type = NULL` until the business owner maps them. | Latest explicit Organization & Identity decision (user brief §2) overrides the earlier free-form tree. Keeping legacy rows untyped avoids inventing a structure (AGENTS §4.4) while allowing E1 schema work to proceed additively. E0 gap G-01/G-02. |
| DEC-056 | Employee becomes the single source of person and organizational data: `identity.employees` owns NIP (unique), full name, email (unique), and employment status. User no longer owns employee display/email data after E3; those columns become deprecated and are not written. | Latest explicit decision: every Employee has NIP/name/email/status and User must not duplicate Employee data. Deprecation instead of immediate column drop follows the no-destructive-migration constraint and keeps rollback possible. |
| DEC-057 | Employee placement is stored in `organization.employee_placements` and points only to an active `DIVISION`; exactly one active placement per Employee is enforced by a partial unique index, with closed rows retained as history. Directorate and Department are derived from Biro/Division ancestry and are never stored on Employee. | Directly implements the locked placement rule and prevents inconsistent organizational columns. Derived values have one source of truth; history remains auditable. |
| DEC-058 | Employee ↔ User is one-to-one: `identity.users.employee_id UUID UNIQUE` references the Employee. During migration the column is nullable; `NOT NULL` is applied only when every account has a verified Employee link. A go-live gate requires zero unlinked accounts; no service-account exception is approved (DEC-068). | Satisfies the 1:1 requirement at database level for linked rows while allowing an additive, non-destructive cutover. Prevents inventing NIPs for the five existing accounts (E0 blocker). |
| DEC-059 | Employee lifecycle and User account lifecycle are separate records and operations. Termination/inactivation of an Employee does not silently rewrite account state; the admin workflow must explicitly deactivate the account, while security operations treat a terminated Employee with an active account as a blocker. | Latest explicit decision says lifecycles are separate. Explicit action preserves audit intent and avoids hidden cascades, while the operational gate prevents terminated staff retaining access. |
| DEC-060 | Individual Employee access reuses the existing `USER` ACL principal via the 1:1 account link; no new Employee principal type is introduced. Distribution, request fulfillment, ownership, and audit keep using stable `users.id`. | Preserves existing ACL, provenance, distribution snapshots, and foreign keys without a risky mass migration. Employee identity is represented by its unique account, and UI can display Employee names. E0 gap G-07/G-09. |
| DEC-061 | Unit-based ACL and unit-scoped role assignments gain `include_descendants BOOLEAN NOT NULL DEFAULT FALSE`. Descendant membership is opt-in per grant/assignment; effective matching uses the user's Biro/Division placement plus its ancestor chain, and explicit DENY with the same scope semantics still wins. | Implements Directorate/Department/Biro/Division access without automatically widening legacy grants. Default false is the non-widening compatibility control required by the locked decision. E0 gap G-09/G-10/G-11. |
| DEC-062 | Legacy unit grants and unit-scoped role assignments are never backfilled to `include_descendants = true`. New grants default false; the UI must show the "include sub-units" option and the effective coverage before saving. Any future bulk widening requires a separate approved data decision. | Directly implements "grant lama tidak boleh otomatis memperoleh cakupan akses lebih luas". Opt-in UI makes scope explicit to administrators. |
| DEC-063 | Employee administration is additive: new `/api/v1/admin/employees` endpoints and permission `employee.manage`; existing `/api/v1/admin/users` and `/admin/users/{id}/units` remain during transition. Responses gain optional Employee/organization fields and do not remove existing fields. | Maintains API compatibility where possible (brief §6) while enabling employee-first management. Old endpoints are retired only after E5/E6 cutover evidence and explicit approval. |
| DEC-064 | Organization/Employee data migration uses only verified HR/business source data. No synthetic NIP, email, unit, or placement may be inserted into a shared environment; synthetic fixtures remain confined to Testcontainers/test environments. V18 enforcement is gated by preflight queries and a signed data-readiness checklist. | Required by "No fabricated employee NIP or organizational records" and protects audit/identity integrity. E0 migration register §4. |
| DEC-065 | Request routing to `UNIT_MANAGER` remains exact-unit during the E-series (no automatic ancestor manager lookup). If Directorate/Department managers must handle descendant Biro/Division requests, that is a separate routing policy decision with its own UAT. | Avoids silently changing who can approve requests as a side effect of hierarchy support. Preserves existing workflow behavior and DEC-035 until explicitly changed. |
| DEC-066 | The bootstrap administrator remains a local SYSTEM_ADMIN account during transition but must be linked to a verified Employee before go-live. The go-live gate query is `count(users WHERE employee_id IS NULL) = 0` for all accounts; DEC-068 confirms no exception is approved. | Keeps first-run bootstrap possible without fabricating an org structure, while enforcing the 1:1 identity model operationally. E0 blocker B-3. |
| DEC-067 | Demo/UAT accounts are **not** made V18-ready by setting them INACTIVE: `employee_id NOT NULL` applies to every row. Hard deletion is prohibited when the account is referenced by audit, ACL, distribution snapshots, requests, or notifications; the dev/UAT database (with `UAT-CO` fixtures and demo accounts) is not the cutover target. V18 readiness requires linking each human account, including the bootstrap admin, to a verified Employee (DEC-066), or an explicit exception with a redesigned enforcement; no data is deleted to make a gate pass. | Answer to the E6 question (2026-11-22): `auditor1`, `employee1`–`employee3` carry audit rows (3–30), ACL grants, a request, distribution recipient snapshots, and notifications; deleting them would erase or mutate audit/business history, and `admin` would still block V18. AGENTS §4.4/§9 (no fabricated data, no hard delete for history). |
| DEC-068 | V18 has **no account exceptions**. Every `identity.users` row in the target database must reference a verified Employee before cutover, including the bootstrap administrator and any demo/UAT account. The gate is a plain table-wide `NOT NULL`; an allowlist cannot satisfy it. A future non-human identity requires a separate account-kind design and an explicit decision, not a preflight exception. | Removes the contradictory "approved exception" wording: an exception could never make `ALTER COLUMN ... SET NOT NULL` pass and invited bypassing the gate. Complements DEC-058/DEC-066/DEC-067 and keeps E6-01 strict. |
| DEC-069 | The bootstrap administrator can be linked at creation with `KCIC_BOOTSTRAP_ADMIN_EMPLOYEE_NIP`, resolved case-insensitively to an existing `ACTIVE` Employee. An unknown or non-ACTIVE NIP aborts startup instead of creating an account; without the setting the pre-V18 behavior is retained with an explicit warning, and a post-V18 unlinked insert fails with an actionable error. The NIP itself is never written to logs or audit. | Closes the DEC-066 bootstrap gap without fabricating an Employee, and prevents a post-V18 first install from producing an account that violates E6-01. Verified by `BootstrapAdminInitializerTest` (linked, unlinked, inactive, unknown NIP). |
| DEC-070 | Pilot role model: `ADMINISTRATOR` (governance penuh setara SYSTEM_ADMIN, konten tetap ACL-gated), `ADMIN` (operasional dokumen/workflow/template/distribusi/audit tanpa manajemen akun/role/organisasi/master data), `PIC` (approver unit setara UNIT_MANAGER tanpa manage_access/archive/restore), dan `EMPLOYEE` ditampilkan sebagai User (Employee). Baseline roles tidak dihapus; routing request menjadi UNIT_MANAGER→PIC, DOCUMENT_ADMIN→ADMIN, fallback SYSTEM_ADMIN→ADMINISTRATOR. Migrasi seed idempotent `V19__pilot_role_model.sql`. | Keputusan pemilik produk 2026-11-23 ("role saya butuh PIC, Admin, Administrator, User (Employee); aksesnya Anda tentukan"). Additive seed menjaga assignment/audit lama; tidak ada privilege escalation otomatis karena konten tetap tunduk pada ACL (ARCHITECTURE §8.3). |
| DEC-071 | Master Organization memiliki tiga submenu — Direktorat, Departemen, Biro/Division — masing-masing halaman CRUD dan tabel sendiri (`/admin/organization/{directorates,departments,divisions}`) plus halaman detail unit (`/admin/organization/units/:unitId`) yang menampilkan rantai hierarki, unit turunan, dan anggota. Halaman Organization lama tetap sebagai tampilan pohon gabungan. Semua route tetap gated `organization.manage` di frontend dan backend. | Keputusan pemilik produk 2026-11-23; tipe unit sudah enforced backend (V14/E1), sehingga pemisahan halaman tidak mengubah aturan hierarki, hanya menyajikannya per tipe. |
| DEC-072 | Rebuild UI memakai arah ui-ux-pro-max: bento-box-grid + data-dense-dashboard, tipografi EB Garamond (display) + Lato (body), radius card 16 px, shadow berlapis, hover lift halus; palet tetap maroon `#8B1A1A` + putih/silver + hitam/soft gold (biru dilarang). Token aktual di `globals.css`; catatan override generator di `design-system/kcic-connect/MASTER.md`. Nomor migrasi role memakai V19 karena V18 tetap dicadangkan untuk cutover E6 sesuai SCHEMA §21.7. | Keputusan pemilik produk 2026-11-23 ("rebuild UI dengan taste ui ux promax; side menu kiri, bento, responsive, palet tetap; jangan terlalu mengikuti design.md; semua fitur tetap ada"). Urutan otoritas: keputusan user terbaru > DESIGN_SYSTEM.md. |
| DEC-073 | Proteksi role sistem dibuka: permission dan status seluruh role sistem (termasuk `SYSTEM_ADMIN`/`ADMINISTRATOR`) dapat diubah lewat API dan UI; lock `setPermissions`/`updateRole` di `RoleAdminService` dan disable editor di frontend dihapus. Guard yang tersisa hanya anti-lockout: administrator terakhir tidak dapat mencabut assignment governance milik sendiri (403). Desain governance konten tidak berubah — assignment global `SYSTEM_ADMIN`/`ADMINISTRATOR` tetap tidak memberi capability konten (DEC-070). | Keputusan pemilik produk 2026-11-23 ("buka perlindungan role sistem"). UI menampilkan peringatan info agar minimal satu administrator aktif mempertahankan akses manajemen role sebelum mencabut permission atau menonaktifkan role; risiko salah konfigurasi menjadi tanggung jawab administrator. |
